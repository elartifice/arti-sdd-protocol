# Repository workflow

Inspect Git state, existing planning, instructions, skills, hooks and user-owned sections before writing. Do not read secret files. The default durable layout is committed `arti_sdd/` planning and `.agents/` shared sources, with `arti_sdd/.state/` ignored. Runtime claims/locks share the common Git directory; branch-local planning and executable code remain on their own revision.

Validate the charter's marked JSON block. Explicit false, none and later decisions are real values. Report detected contradictions and retain their provenance. Existing setup decisions remain in `arti_sdd/config.json`; upgrades never reinterpret rationale or reset choices to heuristic defaults.

Preview the exact operations with `node <skill>/scripts/setup.mjs plan --repo <path> --config <charter-or-json>`. Apply that plan with `setup.mjs apply`; inspect with `setup.mjs check`. Preserve owner content outside protocol markers, unrelated hooks and existing skills. Refuse unreadable, malformed, conflicting or hand-modified managed files; reconcile them before applying. Repeat apply must be stable and interrupted apply must be recoverable.

Installed rituals cover orientation, claim, plan, land and handoff. Reads and discussion do not need a claim. Minimal ticket creation/repair is allowed before claiming; product writes require the selected claim/territory checks. A repeated startup or resume supplies context without resetting an active task or approval. Headless reviewers skip interactive orientation only.

Before landing: verify scope, required checks, DoD evidence and the chosen review policy against the candidate revision. Under manual merge, leave the ticket in review until merge is confirmed. Post-merge close-out records the actual merge, resolves claims/locks, and preserves dirty worktrees. A queued auto-merge is not a completed merge. New work after reopening receives a new revision and fresh evidence; an old merged PR cannot close it again.

Commit approved planning and setup on the actual integration branch before claiming. Setup records its Git metadata reference and mirrors the branch name in config. Claims freeze that integration revision's territory, exclusions, checks, generation, dependencies and risks; editing then reclaiming a working ticket cannot approve a weaker contract. Evidence/status updates remain editable. Contract or policy changes require an owner-approved planning commit on integration before renewed ownership. Review bases must be integration ancestors; closeout checks that integration branch, generation and verification revision. These are trusted local coordination records, not a security boundary against a process that can rewrite Git state.

The core does not bypass branch protection, create remote repositories or publish. Remote claim operations and pushes require the project's existing authorisation. Local-only mode explicitly lacks cross-machine exclusivity.

Remote compare-and-create protects a ticket ID across clones. Territory overlap checks cover active local claims; cross-machine work on different tickets requires coordinator-assigned disjoint territories. Dead recorded coordination owners can be recovered; ownerless or interrupted recovery locks need explicit inspection rather than an unsafe age-based takeover.

For an explicitly authorized new-ticket request, the core provides `scripts/draft.mjs --repo <repo> --session <native-id> --authorization <scope> --title <title> --goal <goal> --territory <JSON-path-list>`. It creates bounded draft metadata without a prior claim. It grants no approval or implementation authority: review and commit the approved contract on integration before claiming. Allocation is atomic within one clone; an interrupted allocation lock requires inspection, not an age-based reset. Strict historical/custom engines that prohibit no-claim planning need an existing or explicitly bootstrapped planning ticket and their own approved adoption; do not bypass those rules with this helper.

For GitHub-first planning, select `planning: "github"`, set `tracker: {"provider":"github","repository":"owner/repo"}`, and use `board: "github"` if desired. Issues hold the ticket contract in an `<!-- arti-sdd-ticket` JSON block, followed by the goal and DoD. Draft IDs use the allocated issue number. No Markdown status mirror is created. Existing local planning is preserved for explicit reconciliation, never silently imported or removed. Run `scripts/tracker.mjs approve --repo <repo> --ticket <ID> --authorization <owner-scope>` to freeze the current authoritative contract locally at the approved integration revision before claiming. Edited requirements need renewed approval. Local claims/checks/review evidence remain private; this is not a cross-clone distributed lock. A closed issue or moved card cannot certify completion: verified merge/check/review closeout closes the issue. If GitHub fails or briefly returns stale inventory, retry the journaled operation after checking its result; never fall back to cached approval. A killed allocation lock needs inspection before removal.

For the final gate, integrate the current integration branch into the ticket candidate before checks; use that integration revision as the explicit base so unrelated landed changes do not become ticket territory. Hold the selected landing lock across final integration/check/review/merge where coordination requires it. Verification rejects an integration branch that advances during checks. Closeout requires the full merged tree to match the tested candidate, as well as both sides of moves/deletions; a new integration result needs current validation and applicable acceptance/review. This keeps focused iteration separate from the one coherent landing gate.

GitHub approval binds the repository, issue number, immutable node ID and normalized contract, not just a reused ticket label. Progress checkbox state is mutable; changing criterion wording, scope, checks or the issue identity needs renewed approval. Evidence belongs in comments or selected receipts rather than silently rewriting approved requirements.

Executable GitHub contracts must begin with the structured marker and be authored by a repository owner, member or collaborator, as reported by GitHub. Public feedback and embedded examples do not become execution tickets. A maintainer creates a bounded execution issue from external feedback before approving it. This prevents public issue bodies from corrupting ticket inventory. If only remote closure fails after verified landing, retry `scripts/tracker.mjs publish --repo <repo> --ticket <ID>`: it rechecks immutable issue/contract identity and current integration ancestry using the durable closeout, without replaying completed model work.

Markdown approval freezes the parsed header (except display status), goal and criterion wording, as well as scope/checks/dependencies. Progress checkboxes and the `## Evidence` section are non-authoritative and remain editable. An optional `approval_expires_at` ISO timestamp is enforced at claim, work and continuation boundaries; a wait cannot extend it. Do not infer an expiry when the owner did not set one.
