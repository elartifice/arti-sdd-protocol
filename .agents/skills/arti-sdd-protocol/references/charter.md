# Project charter

In chat, explain that the result is a blueprint for a coding agent. Establish the product goal, users, stack/surfaces, deployment, constraints and success criteria. Separate confirmed facts from assumptions. Do not infer that a planned UI, deployment or AI feature is absent because no repository exists.

Collect only missing choices: merge policy (`manual` or `auto`); planning (`committed` Markdown or authoritative `github` Issues with an explicit owner/repository); hosts (`claude`, `codex`, `other`); QA (`checks`, `checklist`, `recorded`); team and cross-lab policy (`required`, `risk`, `opportunistic`, `disabled`); and board (`markdown` or an optional hosted `github` Project with a stable URL). Do not preselect cross-lab policy. A risk policy names the relevant risk labels. Explain consequences without imposing this skill's examples on the project.

Use [PROJECT-CHARTER.md.tmpl](../templates/PROJECT-CHARTER.md.tmpl). The marked JSON block is the machine-readable handoff; prose supplies architecture, product milestones and rationale. Leave unknowns explicitly null until resolved. Never invent model access, native host support, source paths or completed tests. A coding agent validates the JSON and inspects the actual repository before setup; it preserves settled decisions while reporting conflicts.

Milestones need a concrete outcome. Tickets name dependencies, territory hints and acceptance evidence. A ticket's pre-merge evidence must not depend on its own post-merge close-out. Product facts and ticket IDs remain editable by the owner; the structured block is the single source for setup choices.

Plan for parallel delivery: every blocking dependency names a required artifact or decision and why it is needed. Ticket numbering, wave labels and milestone order do not create dependencies. Separate planning readiness from implementation readiness: a later milestone can be drafted by a bounded planning ticket once its inputs exist, even while earlier implementation continues. Owner approval still precedes dependent implementation. Identify high-unblock-value enabling tickets, disjoint file territories and actual shared resources; do not reserve entire manifests/schemas for unrelated tickets. One ticket per session permits independent sessions/worktrees. Serialize claims and landing only as required, not whole implementations. Explain ready versus claim-available and give the earliest safe unblock action. Respect an explicitly chosen concurrency cap and label local-only/unsupported host modes.

Distinguish implementation prerequisites (`depends_on`) from integration-only prerequisites (`landing_depends_on`). The latter allow disjoint implementation now but block closeout until the prerequisite's verified landing. Use these only when actual artifacts permit independent work; do not relabel a real build-time dependency just to increase concurrency. Both edge types must be acyclic and name the required artifact.
