# Workflow reliability contracts

Candidate identity is independent of whether a model can review its payload. Checks may run on a complete large candidate; a required review still refuses incomplete or oversized input. Receipts distinguish checks, acceptance, production review and qualification.

Native chat identity, coordination lease identity, repository identity and ticket generation are separate fields. Presentation and wait registrations grant neither ownership nor approval. Existing permanent session-binding policies survive adoption; the public core's releasable ownership is not silently reinterpreted as permanent history.

Ticket requirements, dependencies, territory, checks, risk classification and approval references form a frozen contract. Mutable status and board presentation cannot amend that contract. Changed behavior invalidates affected evidence; unknown impact requires fresh validation/review.

Markdown remains available. An opted-in GitHub adapter makes Issues authoritative and Projects a view, with repository-qualified IDs, versioned contract snapshots, explicit offline/conflict states and separate atomic ownership. A card move is not a claim or completion receipt.

Role context is supplied according to capabilities. A web-only researcher receives a sanitized dossier and collector digest, never instructions to read local files. The coordinator runs the pinned collector; the researcher does not receive shell, credentials or browser sessions. A requested source/window is distinct from fetched coverage. Missing X access must be reported rather than substituted with an assertion of full coverage.

Optional services and wake adapters are installed only when selected. A reminder, a registered wake and a verified resumption are separate outcomes. Wake delivery rechecks native identity, owner, approval, revision and condition before continuation; explicit stop remains effective.

Each adapter reports configured, access-probed, behavior-qualified and live-enforced states separately. Current qualification binds exact package, role and client identities; generated files and historical receipts alone cannot certify changed integrations.

| Boundary | Required identity/proof |
|---|---|
| GitHub contract | Repository, issue number and node ID plus normalized requirements; progress checkboxes cannot approve new wording. |
| File scope and review input | Both lexical entry and resolved target; both rename endpoints; sensitive files never enter a model dossier through aliases. |
| Validation and landing | Candidate includes the integration revision sampled before checks; integration stays stable during checks; the entire merged tree equals the tested candidate, and every landing parent is included in its history. |
| Native continuation | Original host/session, owner nonce, ticket generation, approval, exact candidate and frozen permission choices; actual prerequisite/reset and accepted work. |
| Final review | Current automated/applicable human acceptance, canonical opposite-lab receipt, complete context/coverage and exact candidate; early safety and qualification remain separate purposes. |
